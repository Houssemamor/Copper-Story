# CupperStory

A 2D adventure puzzle game for a Unity course assignment.

**Status: complete and playable.** All four levels are built, the player controller moves
and fights, the three menu screens and both outcome screens work, and Windows and Linux
players build from a clean checkout. 137 EditMode tests pass, including tests that open each
built level scene and check it against the design spec.

All three graded requirements are covered: a menu where the instructions can be read, four
playable levels, and a Win and a GameOver screen. Level 3's locked exit and the Level 4 boss
are the enigmes the *Sujet* asks for.

**Team size:** the brief caps groups at 3, and this team has 4. That exception is approved, so 4 levels are being built. See [The level count rule](#the-level-count-rule).

**Design:** a left-to-right 2D platformer with combat, four named levels ending in a two-phase boss. Full design in `docs/superpowers/specs/2026-10-07-cupperstory-design.md`.

**Art:** CC0 only. The Pixel Frog *Pixel Adventure 1* pack is imported and sliced, and it is
the only pack used. Three assets the spec named are not in it and are substituted: the
player attack animation, the enemies and the boss. See [Assets and
attribution](#assets-and-attribution) and [Deviations from the spec](#deviations-from-the-spec).

## What the brief requires

Transcribed from the assignment screenshots in `docs/`. Graded items and
recommendations are separated, because they are not the same thing.

### Required (graded)

From the brief's *Fonctionnalites* section, these three are what the teacher checks:

1. **A game menu where the player can read the instructions.**
2. **One or more playable levels.**
3. **A GameOver and/or Win interface.**

From *Sujet*: the game is Unity/C#, 2D or 3D, and **the player must solve some
enigmas in order to win**. That rules out a level that is merely walked through.
Something in every level must require thought.

Theme chosen: **Adventure**. The brief lists Adventure as `[solo ou par equipe]`,
so a team is allowed. Aventure also fits the struck-metal setting the project is
named for: a copper being working its way through a mine and a foundry.

### Recommended (not graded, but do them anyway)

- Keep the game responsive.
- Build on Desktop, Mobile and Web.

Validation is a **demo on PC**, so the Desktop build is the one that is actually
demonstrated. This project builds **Windows and Linux** only, which satisfies the
Desktop half. Mobile and Web are recommendations, not graded requirements, so they
are the first things dropped if time runs short.

### Assets and attribution

**Every asset must be CC0 or CC-BY, and CC-BY requires recorded attribution.
Nothing else is acceptable.** This is stricter than the brief, which allows either
creating or importing. It is stricter on purpose: an imported pack with an
unrecorded licence cannot be defended if the teacher asks.

| Role | Pack | Author | Licence | Size | Status |
|---|---|---|---|---|---|
| Terrain tiles, player, enemies, boss, UI, traps, items, backgrounds, FX | Pixel Adventure 1 | Pixel Frog | **CC0 1.0 Universal**, on the pack's own page | 16x16 | **In use, 173 sprites** |
| Gems (gold and silver) | generated by this repo | - | CC0 by construction | 16x16 | `Assets/Art/Generated/`, drawn by `GemArtBuilder` |
| Player attack animation | Knight Hero Platformer Animation Pack | PixiVan | CC0 | 24 px | **Not used.** See deviation 1. |
| Spec's enemy roster | Monsters Creatures Fantasy | LuizMelo | CC0 | 16-24 px | **Not used.** See deviation 2. |
| Spec's boss art | Fire Worm | LuizMelo | CC0 | 51x41 | **Not used.** See deviation 3. |
| Fallback terrain | Pixel Platformer | Kenney | CC0 | 18x18 | On disk outside the repo, **superseded** |

**The pack is Pixel Adventure 1 by Pixel Frog, CC0, and that is settled.**
Source: <https://pixelfrog-assets.itch.io/pixel-adventure-1>. The page states
"Creative Commons Zero v1.0 Universal" in full and says attribution is not
required. The record is `Assets/Art/PixelFrog-PixelAdventure/LICENCE.md`.

Earlier drafts of this file credited the pack to **LuizMelo**, read off the
`hipixelfrog@gmail.com` address printed in the pack's own `Hello.png`. That was
wrong: that address belongs to Pixel Frog, who is a different artist, and
LuizMelo did not publish this pack. The art folder was renamed to
`PixelFrog-PixelAdventure` to match. The LuizMelo packs the spec named
(Monsters Creatures Fantasy, Fire Worm) are genuinely his and are still listed
below as unused.

**The pack cannot supply a player attack animation, and ships no enemies or boss.** Verified
by reading every file name: the four characters have only Double Jump, Fall, Hit, Idle, Jump,
Run and Wall Jump. `20 Enemies.png` is an advert for a separate download, not usable art.

Those three packs were never downloaded, so the game is built without them. The attack is an
invisible hitbox with a cooldown and knockback; the three enemy roles are three movement
patterns drawn with the pack's Rock Head, Spiked Ball and Spike Head; the Slagworm is a
composite of the pack's fire trap. Full reasoning in [Deviations from the
spec](#deviations-from-the-spec).

**Banned, do not import.** These three sit in `../Sprites/` and must stay there:

- `Artwork/` - painterly style, clashes with a 16x16 tileset, no licence file
- `yellow_brown/` - 9-slice tan tiles, wrong style, no licence file
- `ADVENTURER/` - wrong style, no licence file

They also sit **outside this repository**, so a fresh clone never sees them. Do
not copy them into `Assets/`.

**Sprite scale, decided.** The Pixel Frog pack is 16x16 tiles with 32x32 character
cells. At **PPU 16** a 16x16 tile is exactly one world unit and a character is two
units tall, so the grid and the physics agree with no rounding. Kenney's 18x18
tiles would be 1.125 units each, which is why that pack is now a fallback rather
than the terrain source. Settings: **PPU 16, Filter Mode Point, uncompressed, no
mipmaps, no resampling anywhere.** Spike one tile plus one character early. If
they read as mismatched, the scale decision is wrong and should change before
levels get built on top of it.

**The scale was spiked, and it holds.** The one risk the design flagged was that
16x16 tiles and 32x32 characters would read as mismatched. They do not: the character
is exactly two tile heights, both are drawn at the same pixel size inside their own
images, and PPU 16 puts both on the same grid with no rounding anywhere. A tile next
to a standing character at 4x nearest-neighbour confirms it. Nothing in this section
needs revisiting unless the art source changes.

**Never mix the two tilesets in one scene.** 16x16 and 18x18 tiles cannot share a
grid, and the mismatch is obvious on screen.

**Import settings are scripted.** `Assets/Editor/ArtImportSettings.cs` applies PPU,
filter mode, compression and grid slicing to every texture under `Assets/Art/`, so
nobody has to hand-edit a `.meta`. Run it from the **CupperStory** menu, or headless:

```bash
~/Unity/Hub/Editor/6000.6.0f1/Editor/Unity -batchmode -nographics -projectPath "$PWD" \
  -executeMethod CupperStory.EditorTools.ArtImportSettings.Apply -quit
```

It is idempotent. Cell size comes from the `(WxH)` tag in each file name, so
`Run (32x32).png` is cut into 32x32 frames. Current result: 65 sheets sliced into
717 frames, 108 single sprites, 1 left whole because its dimensions do not divide
by its own tag.

**Records.** Every pack copied into `Assets/Art/` keeps its original licence file,
and `Assets/Art/CREDITS.md` records author, source URL and licence for each. The
itch.io packs cannot be downloaded programmatically - the free download needs an
interactive click, so that is a short manual task.

## Game design

Full design in `docs/superpowers/specs/2026-10-07-cupperstory-design.md`. Summary
here so nobody has to open the spec to know what they are building.

**Genre.** Left-to-right 2D platformer with combat. **Theme:** struck metal. The
player is Cupper, a being of copper (Cu). The collectible gems are gold (Au) and
silver (Ag) ore. The final boss is the Slagworm, a creature of forge slag that
corrodes copper. Copper, gold and silver are among the oldest metals humans
worked, which is why the setting is a mine and a foundry.

**The four levels.** Each introduces exactly one new verb before the boss, and
each is one person's file.

| Scene | Name | Teaches | Enemies | Gems |
|---|---|---|---|---|
| `Level01_CopperVein` | Copper Vein | run, jump, attack. No dash. | 3 hoppers | 0 |
| `Level02_SilverRun` | Silver Run | the dash | 5 hoppers, 3 drifters | 0 |
| `Level03_TheLode` | The Lode | two elevated routes, exploration | 6 hoppers, 4 drifters, 3 patrollers | **12: 6 gold, 6 silver** |
| `Level04_TheForge` | The Forge | the boss fight | Slagworm only | 0 |

Level 1 is 125 tiles wide, level 2 is 162, level 3 is 200, and the boss arena is 150 tiles
(2400 px) with a closed ceiling.

**Progression.** Completing a level's goal loads the next one. After the boss
dies, a victory overlay appears and returns to the main menu. There is no
separate ending scene.

**Player verbs.** Run, jump, attack, dash. One dash, usable on the ground or once
in mid-air, resetting on landing, no cooldown timer. Coyote time (0.10 s) and jump
buffering (0.12 s) are not optional polish: without them the game feels broken,
because players press jump just before landing and nothing happens.

**Health.** Three hearts, refilled at checkpoints, 1.0 s invulnerability after a
hit so the player cannot be chain-killed. Death respawns at the last checkpoint.

**Boss.** Slagworm, 12 health, two phases. Above half health it patrols and
throws a fireball every 2.0 s. Below half it enrages permanently: faster patrol,
1.2 s fireball interval, three-shot spread, and a charge every 6 s. Between
attacks it rests 1.2 s and takes double damage. The intended rhythm is dodge,
punish, back off.

**Every level needs a kill floor.** Without one, falling into a pit is an
unrecoverable softlock, because a left-to-right platformer cannot be walked back
from off-screen.

```

```

Open with Unity Hub, let the first import finish (several minutes, this is normal), then

## Running tests

EditMode tests, from the command line:

**Do not pass `-quit`.** Unity quits straight after the first import pass and never
runs a single test. The command completes in a few seconds, writes no results file, and
looks like a success. Without `-quit` the test runner quits itself.

```bash
~/Unity/Hub/Editor/6000.6.0f1/Editor/Unity -batchmode -nographics \
  -projectPath "$PWD" \
  -runTests -testPlatform EditMode -testResults /tmp/results.xml
```

A run takes a couple of minutes while Unity imports; the tests themselves finish in
under a second. Parse `/tmp/results.xml` for the counts.

Single test or fixture, add `-testFilter "LevelFlowTests"`. In the editor, use
Window > General > Test Runner.

EditMode tests live in `Assets/Tests/Editor/`. The folder name is required: Unity only
offers a folder to the test runner if it compiles into an editor assembly, so tests in
`Assets/Tests/EditMode/` build fine and then silently never run.

To force a compile check without the GUI, add `-quit` alone - no `-runTests`.

## Architecture

One scene per level, and a single persistent `GameManager` that survives scene loads via `DontDestroyOnLoad`. The first instance to `Awake` survives; duplicates destroy themselves, so every scene can safely contain one.

Scenes:

| Scene | Purpose | Owner |
|---|---|---|
| `Menu/MainMenu` | Entry point, build index 0. Play / Level Select / Controls / Quit. **Built.** | Person 1 |
| `Menu/LevelSelect` | One button per level, doubles as a dev skip. **Built.** | Person 1 |
| `Menu/Controls` | Control reference table. **Built.** | Person 1 |
| `Levels/Level01_CopperVein` | Movement and attack tutorial | Person 1 |
| `Levels/Level02_SilverRun` | Introduces the dash | Person 2 |
| `Levels/Level03_TheLode` | Gold and silver collection | Person 3 |
| `Levels/Level04_TheForge` | Boss arena | Person 4 |

Win and GameOver are **overlays**, not scenes, and both are built. A level-complete
overlay sits between levels and a victory overlay shows after the boss dies. The brief
asks for a "GameOver and/or Win interface", which an overlay satisfies.

### The win and GameOver screens

One prefab, `Assets/Resources/CupperStory/OutcomeOverlay.prefab`, serves both. It shows
a title, optionally a reason line, and a different set of buttons:

| Screen | Title | Buttons |
|---|---|---|
| Level complete | LEVEL COMPLETE | NEXT LEVEL, MAIN MENU |
| Victory (after the boss) | VICTORY | MAIN MENU |
| GameOver | GAME OVER + your reason | RETRY, MAIN MENU |

`GameManager` creates it the first time a level reports an outcome and hides it again on
the next scene load. **Nobody places anything in a level scene.** A level author still
writes exactly the same two calls, and the screens appear.

It lives under `Resources` rather than being a serialized reference, which is a
deliberate exception to this project's usual avoidance of `Resources.Load`. A
serialized reference would have to be filled in by hand inside each of the four level
scenes, putting a UI concern back into four people's files. One hard-coded path in
`GameManager` is cheaper than that.

The reason line is whatever a level passed to `ReportLevelLost`, so it is free text.
`PixelLabel` uppercases it before looking for glyphs, because the pack's sheet has no
lowercase cells - otherwise the reason would render as blanks next to working buttons.

### The menu screens

All three exist and are generated, not hand-edited.

**Text is drawn from the pack's own font sheet.** The Pixel Frog pack ships
`Menu/Text/Text (Black) (8x10).png`, an 8x10 bitmap alphabet that
`ArtImportSettings` has already sliced into 50 frames. `PixelFont` maps those
50 cells to characters and `PixelLabel` builds one `Image` child per character
of a string. There is no font asset in this project.

This is deliberate. The alternative is TextMeshPro with a smooth TrueType font,
which next to point-filtered 16x16 pixel art looks like a different game
bolted on. Composing glyphs keeps the menus in the same art style as the levels.

The cost is that the menus can only show characters the sheet contains: A-Z,
0-9, and `. , : ? ! ( ) + -` and space. Every display string is uppercase and
avoids `/` for that reason. `MenuText` holds every string in one place so a
test can prove coverage; if you add a string with an unsupported character,
`PixelFont_CoversEveryCharacterTheMenusDisplay` fails and tells you which one.

**Known gap: the Player input action map has no bindings yet.** The Controls
screen documents the intended keys (Move A/D, Jump Space, Attack J, Dash L,
plus gamepad equivalents), so the reference on screen is correct. Until
Person 2 fills in the action map, none of those keys actually move the player.

**Regenerating the scenes.** `Assets/Editor/MenuSceneBuilder.cs` builds all
three scenes from code and re-registers MainMenu at build index 0. Run it from
the **CupperStory** menu, or headless:

```bash
~/Unity/Hub/Editor/6000.6.0f1/Editor/Unity -batchmode -nographics -projectPath "$PWD" \
  -executeMethod CupperStory.EditorTools.MenuSceneBuilder.Build -quit
```

It is idempotent, and it is the only thing you need instead of clicking the
menus together by hand. Do not hand-edit the generated `.unity` files: the
next run overwrites them.

### The integration contract

This is the load-bearing idea of the whole design. **A level author writes exactly two calls and nothing else:**

```csharp
GameManager.Instance.ReportLevelWon();
GameManager.Instance.ReportLevelLost("Your last heart ran out.");
```

No interface to implement. No base class. No scene references to wire up. Your level script decides when the level's goal is met and tells the flow; the flow decides what happens next.

That constraint is what makes four-person parallelism work. Nothing you write requires anyone else's file to change.

### Design decisions, and why

**No UnityEvent wiring.** The textbook Unity way to connect a level trigger to a scene object is Inspector-wiring a UnityEvent. Do not do this. Wiring a scene object into a prefab is stored as a prefab-instance override, and that override lives in the scene file. All four of us would then be editing one file, which is exactly the merge conflict this architecture exists to prevent. A direct static call replaces it.

**No assembly definitions (yet).** Skipped on purpose. In a single `Assembly-CSharp`, a syntax error only stalls whoever wrote it. With per-person asmdefs, forgetting `"references": ["Unity.InputSystem"]` or toggling Enable in the inspector breaks all four compiles on day one. Revisit this only if merge pain actually shows up, not before.

**No `Time.timeScale = 0`.** It breaks `Button` clicks on some Unity versions, and the win and lose screens are buttons. Freeze input with `PlayerMovement.SetInputEnabled(false)` instead.

**Multi-scene rather than one scene with level prefabs.** Both were designed and compared. Prefabs reduce the scene file to a single one, which helps merging, but cost five assembly definitions, a `Resources.Load` string convention, and a break from the convention the course teaches. Multi-scene lets each of us open our own level and hit Play without the others' work being finished, which is what "everyone presents their part" requires.

**Frame rate is set once.** `Application.targetFrameRate = 60` and `QualitySettings.vSyncCount = 0` are applied in `GameManager.Awake`. The brief's "responsive" means a stable framerate, not a responsive layout.

### File ownership

Non-negotiable. Two people editing one file is the failure mode the architecture is designed to prevent.

| Owner | Files |
|---|---|
| Person 1 | `Assets/Scripts/Core/`, `Assets/Scripts/UI/`, `Assets/Tests/`, `Menu/*` scenes, `Level01_CopperVein`, `Assets/Art/` |
| Person 2 | `Assets/Scripts/Player/`, `Assets/Prefabs/Player/`, `Level02_SilverRun` |
| Person 3 | `Level03_TheLode` |
| Person 4 | `Level04_TheForge`, and the Windows/Linux builds |

Each level owner keeps everything under their own `LevelRoot` GameObject and in
their own script namespace, for example `CupperStory.TheLode`.

**This assumes the approved 4-person exception holds.** If it is withdrawn, drop
the Person 4 row and build `Level01` through `Level03`. The architecture does not
change.

## Deviations from the spec

Everything here is a deliberate decision, not an oversight. The spec is
`docs/superpowers/specs/2026-10-07-cupperstory-design.md`; this is the list of places the
built game does not match it, and why.

| # | Spec says | Built as | Why |
|---|---|---|---|
| 1 | Player attack animation from PixiVan Knight Hero | The sword arc is an invisible hitbox; the player uses the pack's existing Idle/Run/Jump frames | The pack was never imported. The attack is felt through the hitbox, the cooldown and the knockback, none of which need an animation. |
| 2 | Mushroom, Flying Eye and Goblin enemies | One enemy archetype with three movement patterns (hop, drift, patrol), drawn with the pack's Rock Head, Spiked Ball and Spike Head | The Pixel Frog pack ships no creatures at all. Three visually distinct sprites cover the three roles, which matters because Level 3 puts all three in one scene. |
| 3 | Slagworm from the LuizMelo Fire Worm, 51x41 | A composite: the pack's fire trap sprite, scaled up for the head and trailed as three segments | Same reason. The three segments follow the head's path, so it reads as a worm in motion rather than as a large blob. |
| 4 | Gold and silver gems as collectibles | Two procedurally drawn 16x16 gems, `Assets/Art/Generated/` | The terrain sheet has no crystal tile. The gems are generated by `Assets/Editor/GemArtBuilder.cs` and committed, so they are CC0-by-construction rather than borrowed. |
| 5 | Input actions at `Assets/Input/CupperStoryControls.inputactions` | `Assets/InputSystem_Actions.inputactions` | Path only. The bindings and the 0.25 stick deadzone are as specified. |
| 6 | Level 2 dash gates of 7 to 9 tiles | Gates of 7 and 8 tiles | A 9-tile gate sits 0.22 tiles inside the 9.22-tile theoretical maximum, so one mistimed dash strands the player at the exact moment the level is teaching the dash. The gates are still impassable without a dash and still clearable with one. |
| 7 | Hearts are the fail state | Three attempts on top of three hearts | Hearts refill at every checkpoint and on respawn, so on their own they can never reach a GameOver screen. The attempt count is what ends a run. |
| 8 | Cupper is a copper-coloured character | The pack's Ninja Frog | It is the only green character of the four, and green is copper's patina. |
| 9 | 1 to 3 people, 1 to 3 levels | 4 levels | The exception is approved by the teacher. If it is withdrawn, drop `Level04` and nothing else changes. |

## Building the players

**This project builds Windows and Linux standalone.** That satisfies the brief's Desktop
requirement, which is what validation actually demos.

From the editor: `CupperStory > Build Windows and Linux`.
Headless, one target per invocation, because that is what Unity takes:

```bash
~/Unity/Hub/Editor/6000.6.0f1/Editor/Unity -batchmode -nographics \
  -projectPath "$PWD" \
  -executeMethod CupperStory.EditorTools.BuildScript.BuildLinux \
  -buildTarget StandaloneLinux64 -quit

~/Unity/Hub/Editor/6000.6.0f1/Editor/Unity -batchmode -nographics \
  -projectPath "$PWD" \
  -executeMethod CupperStory.EditorTools.BuildScript.BuildWindows \
  -buildTarget StandaloneWindows64 -quit
```

Output lands in `Builds/Linux/` and `Builds/Windows/`. They are separate folders because both
players name their data folder after the executable, so a shared folder would leave each
platform with the other's files. `Builds/` is gitignored.

**Use the menu, or these commands, not the editor's Build button.** Unity 6000.6 keeps
a player's scenes on a *build profile* rather than on `ProjectSettings/EditorBuildSettings.asset`,
and a project that has never opened the Build Profiles window gets one with an empty
scene list. Pressing Build in the editor then produces a player with no scenes in it,
with nothing in the log to say so. `ProjectValidator` copies the Build Settings list into
an empty active profile when the editor loads, so the Build button works after the first
open, but `BuildScript` does not depend on that: it passes its own scene list to
`BuildPipeline` and is correct either way. Building from the menu or the command above
is the path that is known to work.

One consequence worth knowing: batchmode has no active build profile, so nothing in this
repository's test or build commands can load a scene by name. That is why the test suite
opens scene files through the editor rather than through `SceneManager`, and why there
are no PlayMode tests.

## Checking the project

`CupperStory > Validate Project` runs `Assets/Editor/ProjectValidator.cs`, which checks the
six failure modes the spec calls out in section 9.2:

| Check | Catches |
|---|---|
| Prefabs | A missing behaviour component, a missing collider, a collider that must be a trigger and is not, and an unwired reference on the player |
| Build settings | A level in the level list but not in the build; a main menu that is not build index 0 |
| Level scenes | Fewer gems than the level requires, so it cannot be won |
| Level scenes | No spawn point, no kill floor, no exit gate outside the boss arena |
| Art licences | An imported pack with no licence file next to it |
| Filter modes | A texture that is not Point, which blurs it against the pixel art |

Every one of these imports cleanly and fails silently in play, which is why they are
checked here rather than found by a player. The build refuses to run while any of them
fails. Headless, and it exits non-zero so a pipeline can gate on it:

```bash
~/Unity/Hub/Editor/6000.6.0f1/Editor/Unity -batchmode -nographics \
  -projectPath "$PWD" \
  -executeMethod CupperStory.EditorTools.ProjectValidator.ValidateFromCommandLine -quit
```

An EditMode test asserts the real project returns no failures, so the validator cannot rot
into a tool nobody runs. That test also creates a colliderless prefab and asserts the
validator rejects it, which is what stops it being vacuously green.

## Rebuilding the levels

The four level scenes are **generated**, not hand-authored. A 2000 px level is over a
thousand tiles, and a sliced sprite's fileID is computed at import, so a hand-written scene
reference imports cleanly and renders nothing.

`Assets/Editor/LevelSceneBuilder.cs` builds all four from a terrain description, along with
the gems, enemies, checkpoints, door, kill floor, camera and EventSystem. `CupperStory >
Build All Levels`, or headless:

```bash
~/Unity/Hub/Editor/6000.6.0f1/Editor/Unity -batchmode -nographics \
  -projectPath "$PWD" \
  -executeMethod CupperStory.EditorTools.LevelSceneBuilder.BuildAll -quit
```

`Assets/Editor/LevelAssetsBuilder.cs` builds the shared prefabs the levels instance: the two

Both are idempotent. Commit the regenerated scenes and prefabs - they are the artefacts the
game runs, and a teammate cloning the repo gets the levels without opening Unity first.

## Things that will cost you debugging time

### Environment

- **The legacy `Input` class does not work.** `activeInputHandler` is `1`, meaning the Input System package only. `Input.GetAxis` and `Input.GetKey` are disabled. Use `UnityEngine.InputSystem`.
- **EventSystem needs `InputSystemUIInputModule`,** not `StandaloneInputModule`. With the Input System active, the legacy module does nothing.

### Architecture

- **Guard against double reporting.** Two objects resolving in the same frame would both call `ReportLevelWon()`. Use a frame lock.
- **The victory overlay must read the level index in `Start`, not `Awake`.** `SceneManager.sceneLoaded` fires *after* `Awake`, so the index is not settled yet. Getting this wrong means the final level shows "Level complete" instead of "Victory".
- **Never modify an instance of `Player.prefab` inside a level scene.** It silently stores an override that resurrects stale values when Person 2 later fixes the prefab, and the bug comes back with no visible cause. Place your own objects beside it instead.

### Gameplay

- **Every level needs a kill floor.** Falling into a pit is otherwise an unrecoverable softlock, because a left-to-right platformer cannot be walked back from off-screen.
- **Respawn falls back to the level spawn point** when no checkpoint was activated. Without that fallback the player respawns at the origin and falls again.
- **A dead enemy is made inert, never destroyed.** Destroying it leaves a dangling reference and risks re-triggering contact damage.
- **Coyote time and jump buffering are load-bearing.** 0.10 s and 0.12 s. Without them, pressing jump just before landing does nothing and the game feels broken.
- **The dash collider stays solid.** Disabling it during a dash lets the player dash through walls and out of the level, a bug class with no upside here.
- **There is no in-game pause menu.** Settings UI is out of scope. Escape works on menu screens only and must not be bound in the in-game action map.
- **A gamepad stick needs a 0.25 deadzone** on both axes, set in the Input Actions asset, or a resting stick creeps the player across the level.

### Build

- **Android signing is not configured.** Android is not a build target for this project, so this only matters if scope changes.
